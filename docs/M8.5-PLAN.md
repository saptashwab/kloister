# M8.5: app-wide UI/UX fixes

Planning baseline: 2026-10-23. Status: approved by the owner on 2026-10-23,
with audit option A (section 3.2). It
addresses the app-wide UI/UX review findings of 2026-10-23. Nothing here changes
ADO transfers (SPEC §7) or the deployment model (SPEC §9).

## 1. Goals and constraints

- Make every screen usable at phone width, make the Audit log readable, and remove
  the small frictions the review found (dates, settings, projects list, export
  placement, My work cards, the drawer's board order field, sign-in branding),
  and add an optional due time (section 4.1, owner request of 2026-10-23).
- No breaking change (the instance is in use). Existing routes and deep links keep
  working; API changes are additive optional fields or new query options; any
  migration is additive (one nullable column and one index). Permissions do not widen anywhere.
- Reuse the M4.5 foundation: tokens only, `ui/` pieces, Angular Material and the
  CDK first (owner preference). New code stays out of the initial bundle, which is
  499.39 kB under the unchanged 500 kB warning budget.
- Every changed screen gets browser tests, including phone-width screenshots in the
  `e2e-report` artifact. Every new or changed endpoint gets permission tests.

## 2. Phone layouts for wide tables

Applies to Members (project settings), Users (admin), Sprints, Backlog and the
Audit log; Projects (section 7) and bucket rows (section 6) follow the same rule.

- Below the phone breakpoint (today only the CSS `max-width: 599px` in the tokens
  and shell; M8.5 adds one shared TypeScript constant for it), each table renders as a
  list of stacked cards: the row's main value as the card title, the other columns
  as labelled lines, and the row's actions in one icon menu. Wider screens keep the
  table unchanged.
- One shared `ui/` pattern built on the CDK `BreakpointObserver` renders either a
  real `<table>` or a `<ul>` of cards from the same row template. Toggling CSS
  `display` on table rows is avoided because it breaks table semantics for screen
  readers.
- Backlog keeps its tree: on phones each row becomes a card with indentation,
  expand/collapse and the multi-select checkbox; bulk actions move into a bottom
  action bar that appears only while something is selected.
- Inline editing in Members (role, visibility) stays available inside the card;
  keyboard order follows the visual order.

## 3. Readable Audit log

### 3.1 Viewer (no audit behaviour change)

- Actions shown as labels ("Signed in", "Item moved", "Admin opened a project they
  are not a member of") from one shared map in `@kloister/shared`, grouped by area
  (Sign-in, Users, Projects, Items, Board, Settings, Backups, ADO) in the filter.
- Actor shown as display name with the email beneath; "System" for entries without
  an actor.
- Entity shown by name: project key and name, item key (`KLO-42`), user display
  name, bucket/label/sprint/team name where the row still exists, otherwise the
  stored id with "(deleted)". Item entities resolve to their key only, never a
  current title. Existing entries already carry some project content in `meta`
  (item titles on create/delete, bucket, label, sprint and team names); the viewer
  shows what is stored, as the raw JSON does today, and adds no new reach.
- `meta` shown as labelled lines for known keys (setting name and new value,
  changed fields, from/to bucket, file name, backup size); the raw JSON stays
  available behind a "Technical details" disclosure.
- Filters: action (grouped), actor (the shared user picker backed by the
  admin-wide user search, since the project picker is project-scoped), project, and
  a date range using the date picker of section 4.
- API: `GET /admin/audit` gains additive read-time fields (`actorName`,
  `projectKey`, `projectName`, `entityLabel`) resolved in batches per page; stored
  rows never change. Admin-only as today; personal-space entries stay excluded.

### 3.2 One cross-project access entry per visit (owner-approved audit change)

Today `ADMIN_CROSS_PROJECT_ACCESS` is written for every API call an admin makes in
a project they are not a member of, so opening one board writes several entries.
Approved rule (option A):

- A read (GET) opens a **visit** for that admin, project and session. Further reads
  in the same project and session are not recorded again while the last recorded
  entry is less than 30 minutes old. After that, the next read records a new entry,
  so long sessions leave one entry per 30 minutes of continued access.
- Every state-changing request (POST, PATCH, PUT, DELETE, for example assigning a
  PM) is always recorded as its own entry, as today, including refused attempts
  (the entry is written before the permission check, as now).
- Every export download (Excel/offline snapshots, ADO files) is also recorded as
  its own entry, although it is a GET (SPEC §6.2 keeps export auditing).
- Entries stay append-only: no row is ever updated. `meta` gains `sessionId` (the
  session row id, never the token) and keeps `via` (the first route of the visit).
- The lookup and insert run in one transaction holding a transaction-scoped
  Postgres advisory lock on (admin, project), so the board's parallel first
  requests cannot write duplicates. An additive index on (`actorId`, `action`,
  `projectId`, `createdAt`) narrows the lookup to the last 30 minutes; the few
  remaining rows are checked for the same `meta.sessionId` in the query.
- A new session (signing in again) always starts a new visit. Entries written
  before M8.5 have no `sessionId` and never count as the current visit.
- SPEC §3.1, the "audited as in 3.1" line of §6 and the export auditing wording of
  §6.2 change to the rule above.

Not chosen: B (keep one entry per call and only group them in the viewer) and C
(A plus grouping of older entries in the viewer).

## 4. Date picker and date format

- One date control everywhere a date is entered (item start/due dates, sprint
  start/end, audit date range): Angular Material's datepicker with a small date
  adapter that reads and writes `YYYY-MM-DD` strings, so no time zone can shift a
  date. Typing is accepted (`2026-10-23` and `23 Oct 2026`), keyboard and screen
  reader support is Material's. Loaded only with the screens that use it.
- One display format, recorded in DESIGN: dates as `23 Oct 2026` (unambiguous in
  every locale), timestamps as `23 Oct 2026, 14:05` in the viewer's time zone (24-hour),
  short card dates as `23 Oct` (year added when it differs from the current year).
  A shared `appDate` pipe replaces the scattered `date: 'medium' | 'short' |
'mediumDate'` uses. Excel/offline snapshots and ADO files keep their own formats.
- Dates still travel as ISO strings.

### 4.1 Optional due time (owner request, approved 2026-10-23)

Two items of the same priority due today look the same, although one due at 17:00
is more urgent than one due any time today. An optional due time separates them.
No start time: the start date is enough.

- Data: additive nullable `WorkItem.dueTime`, minutes after midnight (0–1439).
  `dueDate` stays a calendar date. A time needs a date: setting a time without a
  date is refused, and clearing the date clears the time.
- API: optional `dueTime: "HH:MM" | null` on the item DTO, create, update and bulk
  requests. Clients that do not send it leave the stored time unchanged, so older
  clients and existing calls keep working.
- Meaning: a wall-clock time with no time zone, like due dates today ("today" is
  the viewer's calendar day; server jobs use server time). Everyone sees "17:00".
  An app time zone is out of scope (owner decision); it can be added later without
  converting data, because stored times would simply be read in that zone.
- Display: cards, My work and the drawer show "Today 17:00", "Tomorrow 09:30" or
  "23 Oct, 17:00"; items without a time are shown as today. The drawer offers
  "Add time" next to the due date, using a Material time input loaded with the
  drawer; no time is the default.
- Overdue: a timed item is overdue once its time has passed; an untimed item, as
  today, from the next day. The rule lives in `@kloister/shared` and is used by
  the board, My work, filters, Projects list counts and the overdue notification
  check.
- Order: within the same due day, timed items come first, earliest first, then
  untimed items; ties go by priority, then the existing order. Used by My work
  groups and pagination, the board's due sort and the due filters.
- Not changed: ADO files stay date-only (the export preview warns that due times
  are not exported; imports never set a time). Notifications stay the daily 09:00
  checks; "due within the hour" alerts are a possible later addition.
- Carried along: Excel/offline snapshots add a Due time column; duplication copies
  the time when dates are kept; activity history records time changes; Help &
  FAQ explains the field.

## 5. Page-actions area and the Export… button

- Board, Backlog, Sprints and My work get one page-actions area at the right of the
  page header, next to the view controls. Export… moves there instead of sitting
  below the content.
- At phone width the page actions collapse into one "More actions" icon menu in the
  header. Keyboard and screen-reader names stay "Export…".

## 6. Project settings in section tabs

- Settings split into tabs: General, Members, Teams, Board (buckets, their rules
  and status moves), Labels (labels and label style) and ADO transfer (link to the
  existing transfer screen). Tabs a role cannot use are hidden, as their sections
  are today. A personal space shows General, Board and Labels only.
- Each tab is a child route, `/p/:key/settings/<section>`, using a Material tab nav
  bar; `/p/:key/settings` redirects to the first tab visible to the caller (a Lead
  or a personal space owner may not see General's PM fields), so existing links
  keep working. The tour's settings step goes to the Members tab.
  Unsaved-change handling stays per section.
- Bucket rows: inline rename and the rule selects stay; Up, Down and Delete move
  into one icon menu (Move up, Move down, Delete…) with an accessible name per
  bucket. Board reordering from M7.5 is unchanged.

## 7. A more useful Projects list

- New columns: open items, overdue items and last activity, next to key, name,
  role and status; on phones, stacked cards (section 2).
- Counts respect the caller's visibility scope: the per-project accesses built by
  `ProjectAccessService.memberAccesses()` feed the same filter as
  `ItemsService.scoped()`, so a Member with `OWN` sees counts of their own items
  only. Overdue uses the shared rule of section 4.1 (not Done, and past its due
  time or, without a time, its due date).
- Last activity is the newest audit entry about an item the caller can see
  (create, edit, move between buckets, notes, checklist, files). `updatedAt` is not
  used, because moving a hidden card renumbers visible siblings and would reveal it.
- For projects an admin sees only through "All projects" (not a member), the
  counts are omitted and shown as "—": computing them would be a cross-project
  read. No `ADMIN_CROSS_PROJECT_ACCESS` entry is written by the list, as today.
- API: additive optional `summary: { open, overdue, lastActivityAt } | null` on the
  `GET /projects` list items. Permission tests cover each role and scope, admin
  non-members (null, no audit entry), archived projects and personal spaces (never
  listed).

## 8. Lighter status control on My work board cards

- The full Material select on each status-board card becomes the existing status

  toast, same `statusToBucket` rule; dragging is unchanged. The list view keeps its
  pill.

## 9. The drawer's "Board order" field

- The "Board order" select (listing every card in the bucket) is removed from the
  drawer's fields. The drawer's actions menu gains "Move to top of bucket" and
  "Move to bottom of bucket" for callers who may move the card. The menu is shown
  today only to callers who may delete; it becomes visible when any of its actions
  is permitted (move, duplicate, delete). Precise ordering
  stays on the board (drag or the M6.5 keyboard controls). The move endpoint is
  unchanged.

## 10. Branded sign-in and password pages

- Sign-in and the required password change show the admin's logo and app name
  from the public branding loaded before the first render (no new endpoint). That
  load gives up after 3 seconds; the pages then show the default app name and
  update when a later branding read succeeds. Without a logo, the app name is
  shown as text. The logo's
  alternative text is the app name. Personal theme preferences do not apply before
  sign-in; the admin default theme does, as today.
