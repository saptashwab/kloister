# M8.1: simpler and safer ADO CSV transfers

Planning baseline: 2026-10-23. Implementation follow-up: M8.1 is implemented; the
choices made while building it are recorded in DECISIONS and the user-facing
behaviour in ADO-EXPORT. It builds on [the M8 plan](M8-PLAN.md) and
SPEC §7; where they differ, this plan and SPEC §7.6 apply. The approved M8
storage design, retention and input limits are unchanged except where noted.

## 1. Goals

- Make the everyday transfer short: export, import in ADO, bring one ADO export
  back, done. Keep the thorough M8 review available as a per-transfer option.
- Stop update files from overwriting ADO data that Kloister cannot represent.
- Accept real Azure DevOps Services exports (dates, identities, blank cells) and
  make profile setup a confirmation step instead of manual table entry.
- No breaking change outside ADO transfers (owner condition, 2026-10-23). Items,
  boards, snapshots, permissions, settings and other routes keep their behavior
  and contracts. Migrations are additive with defaults, so `upgrade.sh` applies
  them in place. New profile fields are optional with defaults, so any profile
  saved under M8 still loads. ADO transfer routes and screens may change freely.
- Verify against real exports and manual web-UI imports in a disposable Azure
  DevOps Services organization with Agile, Scrum and Basic projects. The app,
  CI and automated tests still never contact ADO.

## 2. Review modes (SPEC §7.6)

- **Quick** is the default. The export screen produces create files for new
  items and update files for linked ones in one step. A returned ADO export links
  rows by their validated issued reference, applies fields changed on only one
  side since the last confirmed sync, and lists only fields changed on both sides
  for keep/take/skip. One summary (per field and per row kind) is confirmed before
  apply. After linking, the follow-up update file for State and Assigned To is
  offered immediately.
- **Detailed** is a toggle on each transfer and shows the M8 review unchanged:
  every difference needs a choice, links need manual confirmation, rows can be
  selected individually, and parent omission, label creation and per-item
  assignee choice are available.
- A project PM can require Detailed review for the project. Stored as an additive
  `AdoDestination.requireDetailedReview` boolean (default false) so changing it
  does not change the profile revision or invalidate observations.
- Shared in both modes: PM/Lead export and PM-only apply, idempotent retries,
  stale-preview refusal, tombstones, duplicate/unknown reference blocking, no
  automatic users, buckets or sprints, and missing rows never delete anything.
- Each batch records its mode for history and audit (no content in audit meta).

## 3. Fidelity fixes

1. **Update files write only real local changes.** For each linked item, emit a
   field only when the current local value differs from the confirmed local
   baseline (or a Quick/Detailed choice selects it). Otherwise omit the column,
   or repeat the observed raw remote cell where a file shared by several items
   needs the column. Never write back values produced by a lossy mapping: an
   assignee or tag mapped to "none", one status covering several remote states,
   the profile Area Path, or a description whose embedded images were removed on
   import. Tags are merged: unmapped remote tags in the observation are kept.
2. **Real export formats.**
   - Dates: accept ISO and the date/time formats seen in the sample export; when
     a format is ambiguous (day/month order), the profile records the PM's
     confirmed pattern. Values are stored as calendar dates.
   - Blank Priority or other optional cells mean "no value", not an error.
   - Identities: match `Display Name <email>` on the email, case-insensitive,
     against existing aliases and project member emails. Outgoing identities
     default to the member's `Display Name <email>`, matching Microsoft's
     documented import format; ADO resolves them by UPN.
3. **Link-only returns do not block on unrelated columns.** Unmapped State,
   Assigned To, Tags or Iteration values become warnings when they are not
   applied; the observation still records the raw cells.
4. **Generated footers are stripped by structure.** Recognize the generated
   details block by its start marker and the issued reference, so a prepared but
   never imported update file cannot make the next import fail. Edited footers
   still need explicit handling as in M8.
5. **Unapplied previews expire.** Incoming previews and unprepared batches lose
   their stored content after 7 days (approved 2026-10-23); the compact
   receipt and idempotency key remain so retries cannot create duplicates.
6. **Narrower staleness.** The preview digest covers the selected items, their
   ancestors and the members, buckets, sprints and labels they reference, not the
   whole project. Mapping edits re-normalize stored raw observations instead of
   invalidating them; only a destination identity change discards them.
7. **Flat update files.** Update-only files use a single `Title` column. Title
   hierarchy columns stay in create and mixed create files, where Microsoft
   documents them. A local parent change on a linked item is reported as a
   warning to change it in ADO, until the scratch-org drill shows what an
   ID-based hierarchy row does.
8. **Formula guard.** Keep rejecting cells that start with `=`; allow text that
   starts with `+`, `-` or `@` (for example "- fix login") with a preview warning
   not to open transfer files in a spreadsheet. ADO import does not evaluate
   formulas.
9. **Hierarchy warnings.** Warn when an exported parent/child pair is valid in
   Kloister but not a default ADO backlog relation (for example Task under
   Feature, or Issue under Issue in Basic).
10. **One source of presets.** Move preset types and default states into
    `packages/shared/src/ado.ts`, used by both API and web.

## 4. Setup from a sample export

- PMs upload one ADO query export in Transfer settings. A new PM-only
  `POST /projects/:id/ado/sample` endpoint parses it (same limits as imports),
  stores nothing, and returns distinct work item types, states per type, tags,
  iteration paths, identities, date headers and their detected formats.
- The settings form pre-fills suggestions: reverse types from the preset; states
  per type from the preset defaults below; tags to labels and iterations to
  sprints by case-insensitive name; identities to members by email. The PM edits
  and saves as today; nothing is saved without that confirmation.
- Preset default states (suggestions, confirmed against the sample):
  Basic To Do/Doing/Done; Agile New/Active/Resolved/Closed (Task New/Active/
  Closed); Scrum New/Approved/Committed/Done (Task To Do/In Progress/Done); CMMI
  Proposed/Active/Resolved/Closed. Blocked has no default state and is omitted
  (remote state kept) unless the PM maps it.

## 5. Transfer screen

- Show statuses, people, labels, sprints and items by name and key (`KLO-7`)
  instead of raw values, `null` and UUIDs; pluralize counts.
- Move **ADO transfer** after Settings in the project tabs and use real tabs
  (Material tab navigation) for Export, Import, Settings and History.
- Use the shared label colour picker for label creation.
- State the ADO prerequisite on the import step and in ADO-EXPORT: importing
  CSV files into ADO needs Project Administrators (or Team Foundation
  Administrators) membership in that ADO project.

## 6. Files

API: `src/ado/` (export, transfer, csv, profiles, service, controller, dto, a
small `sample.ts`), additive migration for `requireDetailedReview` and the batch
mode, permission and db tests for the sample endpoint and the PM setting.
Shared: `ado.ts` presets, review mode and sample result types. Web:
`pages/ado-transfer/` (mode toggle, summary, readable review, sample upload,
tabs), `core/ado-api.service.ts`, project shell tab order. Docs: SPEC, this plan,
ADO-EXPORT (rewritten around the Quick flow), Help, DECISIONS, OpenAPI.

## 7. Verification

- Local gate as usual; database and browser tests stay CI-only.
- Fixtures: sanitized exports from the disposable organization (names and emails
  replaced with `example.org` values before they are committed), alongside the
  existing hand-written fixtures. Cover all three processes, tree and flat
  queries, dates, identities, blank cells and HTML descriptions.
- Unit tests for every fix in section 3, including round trips proving that
  unmapped assignees, omitted tags, many-to-one states, Area Path and images are
  never overwritten, and that a prepared-but-unused update file does not break
  the next import.
- Manual drill in the disposable organization, through the ADO web UI: create
  import, return/link, state and assignee update, new child under a linked
  parent, both-sides conflict, partial selection, repeated import, and an
  ID-based hierarchy row. Record results locally; only sanitized fixtures and
  documented conclusions are committed.

## 8. Out of scope

App-wide UI/UX improvements from the 2026-10-23 review (phone tables, audit log
readability, date pickers, settings tabs, projects overview) are planned
separately. No live ADO connection, token, sync job or change to the deployment
model.
